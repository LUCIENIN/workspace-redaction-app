当前演示规则

    REPRODUCIBLE WORKFLOW

    真实工作区的六步闭环

    网页是认知入口；命令行脚本才是对文件执行的可复现工作流。

    1. 01

      界定公开范围

      先建“要发布的文件清单”，不对整个私有工作区做默认公开。

    2. 02

      扫描不写入

      以 dry-run 读取文本类文件，统计规则命中，不更改原文件。

    3. 03

      保守替换

      密钥、凭据、联系方式和本机用户路径替换为显式占位符。

    4. 04

      导出隔离副本

      只向新目录写入处理结果；二进制文件与符号链接默认跳过。

    5. 05

      人工双向复核

      既检查“该删的是否仍在”，也检查“不该删的是否被误伤”。

    6. 06

      远程门禁与回读

      GitHub Actions 再扫一次；推送后从远程页面和原始文件地址回读。

    CLI · 默认扫描不写入

    python3 scripts/sanitize_workspace.py scan /path/to/workspace --fail-on high

    CLI · 导出新的脱敏副本

    python3 scripts/sanitize_workspace.py export /path/to/workspace --output /path/to/sanitized-copy

    EXECUTION BASIS

    为什么这样执行

    这里的“执行依据”是工程与授权边界，不是对任何法律、行业或组织合规的自动证明。

    A

    用户明确授权

    只在已确认的账号、仓库、文件范围和动作上执行。

    B

    数据最小化

    不因“以后可能有用”就多复制；不需要公开的内容不进入产物。

    C

    原始证据保留

    不在原件上覆盖脱敏；可核验性与可回退性优先。

    D

    最小权限

    CI 只请求读取仓库内容，脱敏报告不保存敏感原文片段。

    E

    双重验证

    本地检查是一层，远程状态回读是另一层，任一失败都不宣称完成。

    F

    结论有边界

    “未命中”只表示已配置规则没找到问题，不排除未知格式与语义泄露。

    USE CASES & CAUTIONS

    适合什么，不适合什么

    脱敏是风险降低手段，不是对原始数据处理责任的替代。

    SUITABLE

    适合

    • 将内部工作流整理成公开教程
    • 提交可复现的最小问题样例
    • 分享配置模板、日志片段和演示数据
    • 在开源前建立一致的团队门禁

    NOT ENOUGH

    单靠它不够

    • 合同、财务原件、客户记录与生物识别数据
    • 图片、音视频、压缩包和数据库中的隐藏元数据
    • 依赖上下文才能判断的商业机密
    • 已经推送到 Git 历史中的真实密钥
    !

    真实密钥一旦入库，先撤销再清理历史

    删除当前文件不会让旧提交失效。密钥轮换是第一动作。

    !

    二进制文件默认跳过

    图像 EXIF、PDF 隐藏层、Office 修订记录需要专门工具和逐文档检查。

    !

    误报与漏报同时存在

    自动化只能缩小人工复核范围，不能取代对项目语义的理解。

    LAST GATE

    上传前，问自己五个问题。

    1. 01这个文件真的需要公开吗？
    2. 02原始证据是否依然完好保留？
    3. 03报告中是否没有回显敏感原文？
    4. 04是否有另一个人或视角复核？
    5. 05推送后是否能从远程独立回读？
