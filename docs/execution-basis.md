# 本地 LLM Wiki 脱敏工作的执行依据

这里的“执行依据”是当前本地知识库的实际目录、源码和状态证据，不是法律意见或自动合规证明。

## 1. 知识库本身的三层架构

LLM Wiki 将内容分为：

1. 原始资料：`raw/sources/` 保存来源证据。
2. Wiki：LLM 分析后生成带 frontmatter、来源关系和 wikilinks 的持久页面。
3. Schema/Purpose：定义结构规则和知识库存在的目的。

因此，原始资料与生成 Wiki 的隐私等级不同，但两者都不是默认公开资料。

## 2. 本项目的安全同步实现

`sync-codex-knowledge.py` 在进入 Codex 归档前执行候选筛选：

- 跳过符号链接、二进制、依赖、构建产物和超出大小限制的文件。
- 排除 `.env`、认证文件和常见凭据文件。
- 对 API Key、Token、Bearer、云访问键和常见密码赋值做显式替换。
- 只为去秘密后的配置生成结构摘要。
- 在清单中记录脱敏数量、跳过数量和目标文件摘要。

这只能处理格式稳定的秘密，不能识别所有业务语义和隐私关系。

## 3. 图谱与索引是可再生成运行状态

`build-codex-graph.py` 根据受控来源生成技能、工作流、项目、插件、规则和领域节点，并写入内容指纹。向量索引从符合范围的 Wiki Markdown 再生成。

所以公开工作流不需要复制 `.llm-wiki/lancedb/`、对话、队列或其他运行状态；这些内容应留在本机。

## 4. 健康检查使用多类证据

`knowledge_health.py` 不把“有文件”当成知识库健康。它分别检查：

- 断裂 wikilinks 与可行动孤立页。
- 页面类型所需 frontmatter。
- 正向搜索基准与无关噪声查询。
- 图谱内容指纹和向量索引一致性。
- API、搜索与向量状态是否可用。

文件、图谱、搜索和向量是不同证据路径。任一路径未知都不能写成“已完成”。

## 5. 日常同步是五步有界流程

`run-daily-sync.zsh` 当前顺序为：

1. 同步 Codex 安全归档。
2. 修复可以安全推导的来源 frontmatter。
3. 重建 Codex 知识图谱。
4. 审计知识库健康和搜索质量。
5. 执行一次有界本地 AI 维护，并在发生写入后重新验证。

锁、状态 JSON、日志和失败记录用于判断实际结果，但它们本身属于本机运行状态，不进入公开仓库。

## 6. 公开工作流采用“抽取”而不是“整库脱敏”

| 私有层 | 公开处置 |
|---|---|
| 原始资料、私密档案 | 不复制、不上传 |
| 对话、向量、队列、缓存 | 不复制、不上传 |
| Wiki 页面 | 人工识别方法与语义边界，只抽取可复用部分 |
| 工具与工作流 | 去除账户、绝对路径、凭据和项目专有事实后审计 |
| 状态信息 | 只输出聚合数和白名单字段，不输出文件名与内容 |

这比“先复制整库、再寻找敏感字符串”更符合数据最小化原则，也更容易审计公开范围。

## 7. 结论边界

- 自动扫描未命中，只表示已配置规则没有找到匹配。
- 无内容快照只证明该 JSON 没有包含内容、文件名和源路径。
- Wiki 页是否可以公开，仍需要隐私、版权和业务语义复核。
- 已发布结果必须从 GitHub、Raw 文件和 Pages 独立回读。
